Session plan · Section 1 of 603

Anti-pattern: Looks good

Start by demonstrating the KosherCheck application. Then summarize: we built an agentic application with an LLM, ran a few manual tests, and it looks good. Ask whether that is enough to trust it. The image is an existing application screenshot, not a newly executed evaluation. Let the audience suggest what could go wrong before proceeding.

Easy cases. We tried obvious inputs but missed ambiguous ones: plant-based cheese, an unknown sauce or a kitchen with no information about its status.

Nondeterminism. Repeating the same request can produce a different status or explanation. One successful attempt does not establish consistent behavior.

Manual checking does not scale. After a prompt, model or rule change, we cannot keep reviewing hundreds of answers by eye every time.

What else? A correct status can hide an incorrect explanation. Without explicit expectations and saved results, we may miss regressions or remember only successful examples.

Transition: “How do we turn this into a repeatable check?” The next slide explains an eval through the same homework example.

What is an eval?

An evaluation is a test that measures how well an AI system performs a task against explicit criteria.

In the homework, we checked the system’s results against what we expected.

Session plan · Section 2 of 605

How to think about evaluation

Reveal one step at a time with Right, Space, or Next. Ask the question at the bottom and let the audience propose the next improvement before revealing it.

1. Start with personal experience. Qualitative impressions are useful, but they do not yet form a controlled comparison. 2. Use the same task, starting repository and expectations in separate clean runs. 3. Repeat to see variation instead of choosing the best answer. 4. Inspect observable traces: tool names, call counts, time and token usage where available; fewer calls alone do not mean better quality. 5. Include representative tasks you actually care about. Decide which quality and resource tradeoffs matter.

We compare complete configured systems: harness plus model, instructions and tools. This does not isolate which model is better. To attribute a difference to one component, control the other components. There may be different winners for different tasks.

Session plan · Section 3 of 608

Start with a goal

Separate the product goal from the evaluation question. The product helps assess dishes; this evaluation focuses on handling missing information correctly. The wording follows the goal in KosherTestData.cs.

Start with a user need or a failure you care about. Ask what the system should do, under which conditions, and what observable behavior would count as success. You do not need to choose a numeric threshold yet. Here we want to know whether the system requests necessary clarification without inventing uncertainty when the facts already support a decision.

The goal guides the dataset and graders. Unknown soup ingredients should trigger clarification; certified sealed crackers should allow a decision; beef with dairy should not become uncertain merely because the input asks for it.

Session plan · Section 3 of 611

Code, LLM and human graders

Grader and evaluator mean the same thing here. These are three ways to assess an output, and they can be combined. Human grading is actual assessment by a person, not just writing the rubric.

In KosherEvalTests.cs, the code grader compares actual.Status with ExpectedStatus. The service validates the 1,000-character explanation limit; it is shown as a simple example of a code check, not a separate assertion currently implemented in the eval test.

Dima’s LlmJudge.cs evaluates the explanation against ExpectedClarification, ExpectedStatus and ExpectedReasoning. Score 0: required clarification or decision is missing or incorrect. Score 1: it is present, but the reason is missing. Score 2: both are present. Invented dish facts are flagged separately in HasInventedFacts. When no clarification is needed, the answer should explain the decision without introducing uncertainty. Equivalent wording is accepted.

The soup example needs both the missing information about the soup ingredients and the reason: it may contain non-kosher ingredients. Merely saying that the soup ingredients need checking does not satisfy the reasoning criterion.

The previously discussed built-ins are from Microsoft.Extensions.AI.Evaluation.Quality. RelevanceEvaluator uses the question and response; its rubric includes correctness and completeness, not just being on topic. CompletenessEvaluator compares against a required reference answer. These generic rubrics do not replace the product-specific KosherCheck judge.

LLM-as-a-judge

These elements can work together. An assertion checks a specific expectation; a rubric defines score levels; a reference (golden) answer supplies expected content. Next we will examine a built-in scoring rubric.

A judge is often a single LLM call. Provide the input and answer as data, and tell the judge to ignore embedded instructions. Separate criteria can share a call.

When using a ready-made evaluator, read its actual inputs and rubric. A generic relevance evaluator does not replace the product-specific expected-status check.

A reference is optional for LLM judging in general, but mandatory for evaluators designed around one. Microsoft RelevanceEvaluator uses the question and response without a reference; CompletenessEvaluator requires a reference answer. Session plan · Section 3 of 615

RelevanceEvaluator rubric

The five levels are paraphrased from Microsoft.Extensions.AI.Evaluation.Quality.RelevanceEvaluator. This is the built-in 1–5 scale, not the homework judge’s 0–2 scale. The evaluator receives the user question and model response; it does not require a reference answer.

For example, ask which soup information is missing and why it matters. An unrelated answer fits 1. An answer with incorrect information fits 2. Naming the soup ingredients but omitting the requested reason illustrates 3. Addressing both accurately illustrates 4. Relevant additional explanation can support 5. These examples explain the rubric, not guaranteed model scores.

The other previously discussed built-in, CompletenessEvaluator, compares a response with a required reference answer. Its levels progress from missing the reference information to covering all important information. Different evaluator names, inputs and rubrics matter; neither generic evaluator replaces our custom KosherCheck requirements.

Next, distinguish a grader from its recorded metrics and the rule used to accept a result.

Microsoft RelevanceEvaluator: source and full rubric

Implementation details from the supplied source review: RelevanceEvaluator receives QUERY and RESPONSE, not the application system prompt or full history. CompletenessEvaluator receives Response and Ground Truth; without its required context it reports a diagnostic error instead of invoking the judge. Each returns one numeric metric, not a score per rubric item. The shared interpretation accepts valid scores 4–5; this is a library default, not a universal evaluation threshold.

Completeness rubric, paraphrased: 1 — necessary reference information is absent; 2 — only a small part is covered; 3 — roughly half; 4 — most, with some secondary omissions; 5 — all necessary information. The LLM judges coverage and correctness; this is not an exact count of matching statements.

Session plan · Section 3 of 616

Metrics: recording the result

Score and HasInventedFacts are the exact fields in JudgeResult.cs. KosherEvalTests.cs requires Score == 2 and !HasInventedFacts for judgePassed; the complete case also requires codePassed, which checks the expected status. The threshold row here is the judge acceptance rule, not the entire case rule.

Metrics record distinct properties. A length check measures characters; an LLM grader returns a rubric score or flag. Latency and token usage are operational measurements, not necessarily LLM grader outputs. The listed operational metrics are examples, not claims that the homework currently records them. RelevanceEvaluator uses 1–5, not 0–4.

Score is not confidence. Invented facts are evaluated independently: an answer may score 2 and still fail because HasInventedFacts is true. Do not combine seconds, token counts and quality scores into one number without an explicit decision rule.

Session plan · Section 3 of 618

Thresholds and success criteria

The three required conditions match KosherEvalTests.cs: CodePassed checks actual versus expected status; JudgePassed requires Score == 2 and !HasInventedFacts. Score 1 lacks the expected reasoning, so it fails this homework evaluation. These conditions are combined, not averaged.

Latency is shown as an example operational metric that could be collected without a pass/fail threshold; this is not a claim that the homework currently records it. If the product later requires a response within a specified time, add that requirement explicitly. Until then, recorded latency has no effect on this verdict.

Different evaluators use different scales. Microsoft RelevanceEvaluator uses 1–5 and its built-in interpretation accepts valid scores of at least 4. This is separate from the KosherCheck 0–2 scale. Neither scale nor threshold is universal.

Session plan · Section 4 of 622

Comparing system versions

All numbers are illustrative: A 10/20 = 50%, B 18/20 = 90%, C 8/20 = 40%. B improves quality while increasing median latency from 2.8 to 4 seconds. C reduces latency below one second but loses quality. These are separate system configurations, not measurements from the previous single-case example.

For this example, assume both remaining B failures are noncritical and every critical case passes. With an explicit release gate of at least 90% plus all critical cases passing, B can ship if four seconds is acceptable. C fails the quality gate. The 90% threshold is a teaching choice, not a universal recommendation. Check individual regressions, not only averages.

Keep dataset, graders and run conditions comparable. Repeat trials to assess variability. Record prompt versions and per-case failures. If grading rules change, rerun the baseline under the updated rules.

Online evaluation is part of the broader continuous evaluation process. Not every check needs to run on every commit: choose frequency based on risk and cost. Session plan · Section 5 of 624

A failed eval may expose an overly narrow expectation rather than a bad agent solution. Verify the real outcome and requirements before changing the eval. Read complete transcripts and inspect both passing and failing runs.

For a custom LLM grader, request a short evidence-based justification followed by the score in the output schema, for example reason then score. Ask for the words or observed facts supporting the criterion. This is a design to validate, not a guarantee of accuracy: field order alone does not ensure sound judgment.

Human calibration is the additional suggested tip. Compare the judge with human grades on representative good, bad and ambiguous responses, then refine the rubric where necessary.

Session plan · Section 6 of 625

Online evaluation

In production, the system has already answered. You can asynchronously evaluate a saved trace without calling the system again. Historical batches of traces can also be evaluated. The key difference is the available data. The same graders can apply when the necessary input and context are present. Reference-free grading does not guarantee that the judge establishes the truth.

Select traces by the task they are meant to perform. A debugging grader applies to debugging tasks, not every agent request. Do not filter only by tools that were actually called: that excludes cases where the agent should have called a tool but did not. For KosherCheck, grade the final explanation rather than every span.

Session plan · Section 5 of 626

Your eval is a first version, too

Evaluation gives evidence about the behaviors and cases it covers, not a guarantee for every real request. A local run is the starting point. Observe production questions, outcomes and user feedback; review new cases and expectations before adding them.

Improve both the system and its evaluation. Some gaps need new cases, others need new graders or entirely new evaluations. When criteria change, rerun comparable versions under the same updated rules. Do not weaken success rules merely to make failures disappear.
