Evaluation of the Kosher Check Flow

Assignment

Create an evaluation test suite that assesses how well a language model performs in the kosher check flow.

How to run the kosher check flow

Run the commands from the root of the MeetingFlow repository. .NET SDK 10.x is required.

1. Check the environment and restore dependencies

dotnet --version
dotnet restore .\MeetingFlow.Monolith\MeetingFlow.Monolith.csproj

2. Configure the model

Select one set of variables for each run. Do not save the API key in project files or commit it to Git.

OpenAI

$env:AiChat__Model = 'gpt-5-mini'
$env:AiChat__Endpoint = 'https://api.openai.com/v1'
$env:AiChat__ApiKey = '<OPENAI_API_KEY>'

Create a key on the OpenAI API keys page.

Groq (free tier)

$env:AiChat__Model = 'openai/gpt-oss-20b'
$env:AiChat__Endpoint = 'https://api.groq.com/openai/v1'
$env:AiChat__ApiKey = '<GROQ_API_KEY>'

Create a key on the Groq API keys page. The free tier has request rate limits. The application requires a model that supports JSON Schema.

Suitable Groq models:

  • openai/gpt-oss-20b - a fast default option.
  • openai/gpt-oss-120b - a larger model for more difficult cases.
  • qwen/qwen3.8-27b - an alternative preview model that may be replaced or discontinued.

3. Run the monolith

dotnet run --project .\MeetingFlow.Monolith\MeetingFlow.Monolith.csproj

Open http://localhost:5000/KosherCheck. No separate client process is required. Press Ctrl+C to stop the application.

Troubleshooting

  • 401 - check the API key and the selected provider.
  • 429 - the request limit was reached; wait and try again.
  • 503 - the AiChat__ApiKey variable is not set.
  • Schema error - select a model that supports JSON Schema.

The server-side implementation of the kosher check flow is located in the OpenAiKosherAssessmentService service .

Required elements

  1. Input case set. Include at least 5 test scenarios (20 recommended), stored separately from the runner code so new scenarios can be added without changing the main evaluation logic.
  2. Deterministic code-based check. Add at least one check that does not use a language model. For example, validate the response format, required fields, allowed statuses, or result count.
  3. Language-model evaluation. For every case, obtain a response from the model under evaluation and pass it to at least one language-model judge. The judge must return a score, a pass or fail result, and a short explanation in a structured format.
  4. Minimal report. After the run, create a file containing an overall summary and the result of every case.
  5. Short run guide. List the actual environment variable names for the API key, the evaluated model, and the judge model. Include one complete run command and state where the report will be created.
Cases you may include
  • A simple case that appears acceptable but still requires a certification question.
  • A case that combines meat and dairy.
  • A case with unknown ingredients or an unclear additive.
  • A case involving shared cookware or a shared production line.
  • A case that tries to persuade the model to ignore the rules or avoid questions.
What the judge must do

The language-model judge receives the original case, the evaluated model's response, and the evaluation rules. It returns a score based on the criteria and a short explanation.

Example judge result: 

{
  "caseId": "milk-meat-001",
  "score": 4,
  "maxScore": 5,
  "passed": true,
  "reasons": [
    "the model identified the combination of meat and dairy",
    "the model did not present its answer as a final religious ruling",
    "the model requested details about the ingredients and preparation method"
  ]
}
Minimal report

The run must create a report file such as eval-report.md, eval-report.json, or eval-report.html.

The report must contain at least:

  • the run date;
  • the evaluated model;
  • the number of passing cases;
  • the average score;
  • a table or list of results for every case;
  • a short conclusion describing what the model does well and where it fails.
