Обзор тестирования MeetingFlow

Практический пример компонентных, точечных интеграционных и системных интеграционных тестов в микросервисном приложении.

Состав набора: 13 исполняемых компонентных сценариев, один точечный интеграционный тест и один системный интеграционный тест backend. Большинство сценариев намеренно остаются на компонентном уровне, а дорогие тесты используются только для рисков, которые нельзя надёжно проверить изолированно.

1. Компонентные тесты SchedulingEngine

SchedulingEngine содержит бизнес-правила расписания и проверки вместимости. У него нет внешних инфраструктурных зависимостей.

xUnit → HttpClient → WebApplicationFactory → настоящий SchedulingEngine

WebApplicationFactory<Program> запускает настоящее ASP.NET Core-приложение внутри процесса тестов. Запрос проходит через routing, model binding, validation, бизнес-логику и JSON-сериализацию. Docker не требуется.

Theory для проверки конфликтов

CheckConflict_ForValidSessions_ReturnsExpectedResult

Что показывает: Одно правило расписания выполняется с четырьмя наборами данных: пересекающиеся сессии в одной комнате, соседние интервалы, пересекающиеся сессии в разных комнатах и интервал непосредственно перед существующей сессией.

Чему учит: Использовать xUnit Theory, когда структура Arrange, Act и Assert остаётся одинаковой, а меняются только входные данные и ожидаемый результат. Каждая строка InlineData всё равно отображается как отдельный test case.

CheckConflict_WhenCandidateHasInvalidTimeRange_ReturnsValidationProblem

Что показывает: Сессия, время окончания которой раньше времени начала, возвращает 400 Bad Request с ValidationProblemDetails.

Чему учит: Валидация является частью публичного HTTP-контракта. Этот сценарий остаётся отдельным Fact, потому что проверяет другое поведение и другой тип ответа.

CheckCapacity_WhenPlacesAreAvailable_ReturnsRemainingPlaces

Что показывает: Для площадки на 100 мест с 76 регистрациями система сообщает о наличии мест и возвращает 24 свободных места.

Чему учит: Проверять и бизнес-решение, и конкретное вычисленное значение, а не только HTTP-статус.

CheckCapacity_WhenCapacityIsNegative_ReturnsValidationProblem

Что показывает: Отрицательная вместимость отклоняется с ошибкой валидации.

Чему учит: Компонентные тесты должны проверять некорректные данные на публичной границе, а не только happy path.

Главный вывод: Граничные случаи расписания следует проверять быстрыми компонентными тестами SchedulingEngine. Их не нужно повторять через всю микросервисную систему.

2. Компонентные тесты DataAccessor

DataAccessor отвечает за persistence. Его PostgreSQL считается частью компонента и не заменяется mock-объектом.

xUnit → HttpClient → WebApplicationFactory → настоящий DataAccessor → PostgreSQL 16 Testcontainer

Fixture создаёт новый контейнер PostgreSQL, передаёт приложению динамическую connection string и запускает обычный DataAccessor. Production startup создаёт схему и seed-данные. После завершения класса Testcontainers удаляет контейнер базы вместе с данными.

GetMeeting_WhenMeetingExists_ReturnsGraphLoadedFromPostgreSql

Что показывает: Встреча загружается из настоящего PostgreSQL вместе с venue, sessions, registrations и feedback. В HTTP-ответ не попадают внутренние поля.

Чему учит: Один сфокусированный компонентный тест может проверить реальный EF Core query, связи, mapping entity-to-DTO, HTTP-сериализацию и защиту от утечки внутренних данных.

CreateRegistration_WhenReferencesExist_PersistsItInPostgreSql

Что показывает: Тест записывает регистрацию через HTTP API, а затем читает её через отдельный endpoint.

Чему учит: Повторное чтение доказывает, что строка действительно сохранена в PostgreSQL, а не просто возвращена как объект в памяти.

GetMeeting_WhenMeetingDoesNotExist_ReturnsNotFound

Что показывает: Неизвестный идентификатор встречи возвращает 404 Not Found.

Чему учит: Негативное поведение API также следует проверять с реальной persistence-технологией.

Главный вывод: In-memory provider не даёт такой же уверенности в SQL, связях, ограничениях и особенностях PostgreSQL. Для этой компонентной границы подходит одноразовая настоящая база.

3. Компонентные тесты RegistrationsManager

RegistrationsManager координирует работу других сервисов. Сам Manager настоящий, а внешние зависимости заменены контролируемыми test doubles.

→ WireMock DataAccessor stub xUnit → настоящий RegistrationsManager → WireMock SchedulingEngine stub → SpyEventPublisher → фиксированный TimeProvider

WireMock возвращает детерминированные HTTP-ответы. Spy запоминает опубликованные события без запуска RabbitMQ. Фиксированный TimeProvider делает расчёт цены воспроизводимым.

CreateRegistration_WhenDependenciesSucceed_OrchestratesFlowAndPublishesEvent

Что показывает: Manager получает контекст встречи и участника, загружает существующие регистрации, проверяет вместимость, нормализует тип билета, рассчитывает цену, сохраняет регистрацию и публикует RegistrationCreatedV1.

Чему учит: Orchestration-компонент нужно проверять и по публичному результату, и по исходящим контрактам: телам HTTP-запросов, routing key и содержимому интеграционного события.

CreateRegistration_WhenAttendeeAlreadyRegistered_StopsBeforeCapacityCheck

Что показывает: Существующая регистрация приводит к 409 Conflict. SchedulingEngine не вызывается, событие не публикуется.

Чему учит: Проверять отсутствие ненужных вызовов и side effects. Это защищает правильный порядок бизнес-операций и early exit.

CreateRegistration_WhenMeetingIsFull_DoesNotPersistOrPublish

Что показывает: Если SchedulingEngine сообщает об отсутствии мест, Manager возвращает 409 Conflict, не сохраняет регистрацию и не публикует событие.

Чему учит: Бизнес-ошибка должна останавливать все последующие side effects.

Зачем fixture нужен Reset()

Одна fixture используется несколькими тестами. Reset() очищает WireMock mappings, историю HTTP-запросов и события внутри spy перед каждым сценарием. Это не позволяет одному тесту влиять на другой.

Главный вывод: Manager отвечает за orchestration, а не за PostgreSQL или RabbitMQ. Его ветвление дешевле проверять с контролируемыми stub и spy, а причины падения таких тестов проще диагностировать.

4. Точечный интеграционный тест RabbitMQ

Этот тест проверяет одну рискованную асинхронную интеграцию, а не весь application flow.

настоящий EventPublisher → RabbitMQ Testcontainer → настоящий consumer NotificationsAccessor → PostgreSQL Testcontainer

RegistrationCreatedEvent_IsDeliveredAndPersistedAsNotification

Что показывает: Production publisher отправляет RegistrationCreatedV1 через настоящий RabbitMQ. Настоящий consumer получает событие и сохраняет уведомление в настоящем PostgreSQL.

Что проверяет: Exchange, routing key, queue binding, JSON-контракт события, совместимость producer и consumer, обработку сообщения и persistence уведомления.

Чему учит: Использовать targeted integration test для конкретной рискованной границы, не поднимая Gateway, Managers, SchedulingEngine и несвязанные части системы.

Синхронизация асинхронного сценария

Перед публикацией fixture ждёт, пока RabbitMQ покажет активного consumer. После публикации тест polling’ом проверяет HTTP API NotificationsAccessor до истечения ограниченного timeout. Длинный фиксированный delay не используется.

Главный вывод: Нужно ждать наблюдаемого состояния, а не угадывать, сколько времени займёт асинхронная обработка.

5. Системный интеграционный тест backend

Системный тест использует настоящую backend-топологию, предварительно запущенную локально через Docker Compose, и входит через публичный API Gateway.

test → Gateway → RegistrationsManager → DataAccessor → PostgreSQL ├→ SchedulingEngine └→ RabbitMQ → NotificationsAccessor → PostgreSQL

CreateRegistration_ThroughGateway_PersistsAndSendsNotification

Что показывает: Запрос на регистрацию проходит через настоящие Gateway, Manager, Engine, Accessor, PostgreSQL, RabbitMQ и consumer уведомлений.

Что проверяет: Gateway возвращает созданную регистрацию, регистрацию можно повторно получить через Gateway, а асинхронное уведомление становится доступно через NotificationsAccessor.

Чему учит: System test должен проверять критический пользовательский flow через публичную backend-границу, не привязываясь ко всем внутренним деталям реализации.

Локальное окружение и xUnit

docker compose up --build → ожидание готовности локального backend → запуск или отладка теста через VS Code Testing → docker compose down, когда нужны чистые данные

SystemIntegrationFixture подключается к фиксированным локальным адресам Gateway и NotificationsAccessor, проверяет readiness и создаёт HttpClient. Он не запускает и не останавливает Docker.

Тестовые данные и cleanup

Тест создаёт регистрацию и уведомление в локальной базе. Данные остаются после теста, поэтому для повторного чистого прогона нужно пересоздать Compose-окружение. Позже эту же последовательность при необходимости можно автоматизировать скриптом или CI workflow.

Главный вывод: Системный тест может подключаться к настоящему локально запущенному backend и оставаться удобным для запуска и отладки из IDE. Автоматизацию окружения можно добавить отдельно, когда она понадобится проекту.

6. Testcontainers и Docker Compose

Оба подхода запускают настоящие Docker-контейнеры. Testcontainers — это библиотека для программного управления контейнерами, а Docker Compose описывает и управляет полной топологией сервисов.

УровеньЧто запускаетсяКто управляет lifecycle
SchedulingEngine componentОдин сервис внутри test processWebApplicationFactory
DataAccessor componentСервис и PostgreSQLxUnit fixture и Testcontainers
Точечная RabbitMQ integrationPublisher, consumer, RabbitMQ и PostgreSQLxUnit fixture и Testcontainers
Backend system integrationПолная микросервисная топологияShell runner или CI и Docker Compose

7. Как избежать дублирования

РискСамый дешёвый подходящий уровеньЧто не повторяем выше
Пересечение времени и правила вместимостиSchedulingEngine componentВсе edge cases в system test
EF queries, связи и mappingDataAccessor componentДетальное поведение SQL через весь flow
Порядок вызовов и early exitRegistrationsManager componentВсе негативные ветки через Docker Compose
RabbitMQ wiring и контракт событияTargeted integrationДиагностику messaging через всю систему
Совместимость развёрнутой топологииSystem integrationДостаточно одного критического happy path
Итог: Каждый риск следует проверять на самом низком уровне, который способен дать надёжную уверенность. Компонентные тесты объясняют причины ошибок, точечные интеграционные тесты доказывают совместимость на рискованных границах, а системный тест подтверждает, что критический backend flow работает целиком.
