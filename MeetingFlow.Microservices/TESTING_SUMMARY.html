MeetingFlow Testing Summary

A practical example of component, targeted integration, and backend system integration tests in a microservice application.

Test suite: 13 component test cases, one targeted integration test, and one backend system integration test. The suite intentionally keeps most scenarios at the component level and uses expensive tests only for risks that cannot be covered reliably in isolation.

1. SchedulingEngine Component Tests

The SchedulingEngine contains scheduling and capacity business rules. It has no external infrastructure dependencies.

xUnit → HttpClient → WebApplicationFactory → real SchedulingEngine

WebApplicationFactory<Program> starts the real ASP.NET Core application inside the test process. Requests pass through routing, model binding, validation, business logic, and JSON serialization. Docker is not required.

Conflict detection Theory

CheckConflict_ForValidSessions_ReturnsExpectedResult

What it shows: One scheduling rule is executed against four different datasets: overlapping sessions in the same room, adjacent sessions, overlapping sessions in different rooms, and an interval immediately before an existing session.

What it teaches: Use an xUnit Theory when the Arrange, Act, and Assert structure stays the same and only input data and the expected result change. Every InlineData row is still reported as an independent test case.

CheckConflict_WhenCandidateHasInvalidTimeRange_ReturnsValidationProblem

What it shows: A session whose end time precedes its start time returns 400 Bad Request with ValidationProblemDetails.

What it teaches: Validation is part of the public HTTP contract. This remains a separate Fact because it verifies different behavior and a different response type from the successful conflict checks.

CheckCapacity_WhenPlacesAreAvailable_ReturnsRemainingPlaces

What it shows: A venue with 100 places and 76 registrations has capacity and returns 24 available places.

What it teaches: Assert both the business decision and the calculated value, not only the HTTP status.

CheckCapacity_WhenCapacityIsNegative_ReturnsValidationProblem

What it shows: Negative venue capacity is rejected with a validation response.

What it teaches: Component tests should cover invalid input at the public boundary, not only happy paths.

Main lesson: Scheduling edge cases belong in fast SchedulingEngine component tests. They do not need to be repeated through the full microservice system.

2. DataAccessor Component Tests

The DataAccessor owns persistence behavior. Its PostgreSQL database is treated as part of the component and is not mocked.

xUnit → HttpClient → WebApplicationFactory → real DataAccessor → PostgreSQL 16 Testcontainer

The fixture creates a fresh PostgreSQL container, injects its dynamic connection string, and starts the normal DataAccessor application. The production startup creates the schema and seed data. Testcontainers removes the database container and its data after the test class finishes.

GetMeeting_WhenMeetingExists_ReturnsGraphLoadedFromPostgreSql

What it shows: A meeting is loaded with its venue, sessions, registrations, and feedback from a real PostgreSQL database. The response also excludes internal-only fields.

What it teaches: A persistence component test can verify the real EF Core query, relationships, entity-to-DTO mapping, HTTP serialization, and protection from internal data leakage in one focused boundary.

CreateRegistration_WhenReferencesExist_PersistsItInPostgreSql

What it shows: The test writes a registration through the HTTP API and reads it back through a separate endpoint.

What it teaches: Reading the registration again proves that the row was committed to PostgreSQL rather than merely returned as an in-memory response object.

GetMeeting_WhenMeetingDoesNotExist_ReturnsNotFound

What it shows: An unknown meeting identifier returns 404 Not Found.

What it teaches: Negative API behavior should also be verified against the real persistence technology.

Main lesson: An in-memory provider does not give the same confidence in SQL, relationships, constraints, and PostgreSQL-specific behavior. A disposable real database is appropriate for this component boundary.

3. RegistrationsManager Component Tests

The RegistrationsManager coordinates other services. The Manager itself is real, while its external dependencies are controlled test doubles.

→ WireMock DataAccessor stub xUnit → real RegistrationsManager → WireMock SchedulingEngine stub → SpyEventPublisher → fixed TimeProvider

WireMock provides deterministic HTTP responses. The event publisher spy records published events without starting RabbitMQ. A fixed TimeProvider keeps price calculations deterministic.

CreateRegistration_WhenDependenciesSucceed_OrchestratesFlowAndPublishesEvent

What it shows: The Manager reads meeting and attendee context, loads existing registrations, checks capacity, normalizes the ticket type, calculates the price, persists the registration, and publishes RegistrationCreatedV1.

What it teaches: An orchestration component should be tested through both its public result and its outgoing contracts: HTTP request bodies, routing key, and integration event contents.

CreateRegistration_WhenAttendeeAlreadyRegistered_StopsBeforeCapacityCheck

What it shows: An existing registration causes 409 Conflict. SchedulingEngine is not called and no event is published.

What it teaches: Verify the absence of unnecessary calls and side effects. This protects the order of business operations and early-exit behavior.

CreateRegistration_WhenMeetingIsFull_DoesNotPersistOrPublish

What it shows: When SchedulingEngine reports no capacity, the Manager returns 409 Conflict, does not persist a registration, and does not publish an event.

What it teaches: A business failure must stop all later side effects.

Why the fixture has Reset()

The fixture is shared by several tests. Reset() clears WireMock mappings, HTTP request history, and recorded spy events before each scenario. This prevents one test from affecting another.

Main lesson: The Manager is responsible for orchestration, not for PostgreSQL or RabbitMQ. Its branching logic is cheaper and easier to diagnose with controlled stubs and spies.

4. Targeted RabbitMQ Integration Test

This test verifies one risky asynchronous integration rather than the entire application flow.

real EventPublisher → RabbitMQ Testcontainer → real NotificationsAccessor consumer → PostgreSQL Testcontainer

RegistrationCreatedEvent_IsDeliveredAndPersistedAsNotification

What it shows: The production publisher sends RegistrationCreatedV1 through a real RabbitMQ broker. The real consumer receives it and persists a notification in a real PostgreSQL database.

What it verifies: Exchange configuration, routing key, queue binding, JSON event contract, producer/consumer compatibility, consumer behavior, and notification persistence.

What it teaches: Use a targeted integration test to cover a specific high-risk boundary without starting Gateway, Managers, SchedulingEngine, and unrelated services.

Asynchronous synchronization

The fixture waits until RabbitMQ reports an active consumer before publishing. After publishing, the test polls the observable NotificationsAccessor HTTP API until a bounded timeout. It does not use a fixed long delay.

Main lesson: Wait for observable state instead of guessing how long asynchronous processing will take.

5. Backend System Integration Test

The system test starts the real backend topology and enters through the public Gateway API.

test → Gateway → RegistrationsManager → DataAccessor → PostgreSQL ├→ SchedulingEngine └→ RabbitMQ → NotificationsAccessor → PostgreSQL

CreateRegistration_ThroughGateway_PersistsAndSendsNotification

What it shows: A registration request travels through the real Gateway, Manager, Engine, Accessor, PostgreSQL, RabbitMQ, and notification consumer.

What it verifies: The Gateway returns the created registration, the registration can be read again through Gateway, and the asynchronous notification is eventually observable through NotificationsAccessor.

What it teaches: A system test should cover a critical user flow through the public backend boundary without asserting every internal implementation detail.

Why Docker Compose is outside the xUnit fixture

run-system-tests.sh → docker compose up --build → wait for HTTP readiness → wait for the RabbitMQ consumer → pass dynamic URLs to xUnit → dotnet test --filter Category=System → collect logs on failure → docker compose down --volumes

The shell runner owns the full environment lifecycle. SystemIntegrationFixture only reads service URLs, checks readiness, and creates HttpClient instances. It does not start or stop Docker.

Test data and cleanup

Every run creates a uniquely named Compose project with dynamic host ports. It receives fresh seed data, and the test creates a registration and notification. Individual rows are not deleted. The runner removes the entire temporary environment, containers, network, and volumes after the test. An existing local MeetingFlow environment remains untouched.

Main lesson: Full-system infrastructure is easier to manage from a dedicated runner or CI step, while xUnit remains focused on system behavior.

6. Testcontainers and Docker Compose

Both approaches start real Docker containers. Testcontainers is a library for programmatic container orchestration; Docker Compose describes and manages a complete service topology.

7. Avoiding Duplicated Coverage

RiskCheapest suitable levelWhat is not repeated above
Time overlap and capacity rulesSchedulingEngine componentEvery scheduling edge case in the system test
EF queries, relations, and mappingDataAccessor componentDetailed SQL behavior through the full flow
Call order and early exitsRegistrationsManager componentEvery negative branch through Docker Compose
RabbitMQ wiring and event contractTargeted integrationMessaging diagnostics through the entire system
Compatibility of the deployed topologySystem integrationOnly one critical happy path is required
Final takeaway: Test each risk at the lowest level that can provide reliable confidence. Component tests explain failures, targeted integration tests prove compatibility at risky boundaries, and the system test confirms that the critical backend flow works as a whole.
