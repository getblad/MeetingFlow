MeetingFlow Testing Pyramid

Coverage is placed at the lowest level that can verify the risk reliably. As tests move upward, they become broader, slower, and fewer.

System — 1 scenario Complete backend registration flow
Targeted integration — 1 scenario Real RabbitMQ producer-to-consumer compatibility
Component — 13 executable cases SchedulingEngine 7 · DataAccessor 3 · RegistrationsManager 3
The rule: use many focused component tests for business decisions, a small number of targeted integration tests for risky boundaries, and very few system tests for critical flows.

Component coverage

SchedulingEngine

HTTP → real SchedulingEngine
  • Overlapping sessions
  • Adjacent time boundaries
  • Different rooms
  • Invalid time range
  • Capacity calculation
  • Invalid capacity

Why here: these are local, stateless business rules with no external infrastructure.

DataAccessor

HTTP → real DataAccessor → real PostgreSQL
  • Load a meeting graph
  • Map entities into safe DTOs
  • Create and read registration
  • Return Not Found

Why here: EF queries, relationships, mapping, and persistence require the service and its owned database.

RegistrationsManager

HTTP → real Manager → controlled dependencies
  • Successful orchestration
  • Ticket normalization and price
  • Duplicate registration early exit
  • Full meeting early exit
  • No forbidden side effects

Why here: the risk is orchestration and branching, not the behavior of every downstream service.

Targeted integration coverage

real EventPublisher → real RabbitMQ → real NotificationsAccessor consumer → real PostgreSQL

The targeted integration test proves that two application sides agree on the production messaging contract. It covers exchange and routing configuration, queue binding, event serialization, consumption, and notification persistence.

Intentionally excluded: Gateway, Managers, SchedulingEngine, and unrelated flows. Starting them would make the test broader without increasing confidence in this specific integration.

System coverage

test → Gateway → RegistrationsManager → DataAccessor → PostgreSQL ├→ SchedulingEngine └→ RabbitMQ → NotificationsAccessor → PostgreSQL

The system test verifies one critical backend flow:

  1. Create a registration through Gateway.
  2. Read the persisted registration through Gateway.
  3. Observe the asynchronous registration notification.

The complete backend is started locally with Docker Compose before the test. The xUnit fixture connects to the fixed local Gateway and NotificationsAccessor addresses and verifies that they are healthy. This makes the test available through the IDE's Run and Debug actions.

For CI or a larger project, the same local sequence can later be automated with a script or workflow step.

Intentionally excluded: all scheduling edge cases, all Manager rejection branches, and detailed database behavior. Those risks are already covered more cheaply below.

Coverage map: risk to test level

Risk Covered at Why this level Not repeated in
Scheduling rules and edge cases SchedulingEngine component Pure logic behind one HTTP boundary Integration and system tests
EF Core queries, relations, and mapping DataAccessor component Requires the real persistence component and PostgreSQL System assertions
Call order, early exits, and side effects RegistrationsManager component Controlled dependencies make branches deterministic Full-system negative scenarios
RabbitMQ wiring and event compatibility Targeted integration Requires real producer, broker, and consumer behavior Component tests
Compatibility of the deployed topology System integration Requires all real services, configuration, and infrastructure Only one critical flow is needed

What each level tells us when it fails

Failed levelLikely meaningDiagnostic scope
ComponentA rule, contract, mapping, or orchestration decision is brokenOne service
Targeted integrationTwo real components or their infrastructure contract are incompatibleOne integration boundary
SystemThe deployed services cannot complete the critical flow togetherThe complete backend topology

Final takeaway: component tests explain failures, targeted integration tests prove compatibility, and the system test confirms that the complete user flow works.
